## 0. Goal and the loop to prove
One approved input selects a Scroll tile, the page scrolls, a later selection returns to the communication view of the SAME paired participant, and a request can still be sent. Commands: `scroll-up`, `scroll-down`, `back`, `return-to-communication` (frozen `BrowserAction`), plus the ordinary Pause that already exists. No typing, clicking, forms or OS control. Camera data never leaves the device.

## 1. Architecture decision
**Chosen: persistent Chrome MV3 side panel hosting the built Motif app (the ONE visible camera/runtime), plus a service worker used only as a command executor.**
- Panel page `sidepanel.html` = the normal Motif React app (camera, FaceTracker, MotifSession, scanning, care client, Browser controls card). MediaPipe model and WASM are packaged at the extension root so the existing absolute paths `/mediapipe/wasm` and `/models/face_landmarker.task` resolve unchanged.
- Worker: no tracker, UI or camera. Receives validated panel messages and runs `scripting.executeScript` (scroll) or `tabs.goBack` (back) on ONE bound tab. State only in `chrome.storage.session` (MV3 workers are suspended). Reason for a worker at all: privilege separation, because only the small worker holds tab/scripting calls and re-validates what it can; it does NOT make staleness decisions (see 3.4).
- Return to communication is a scan-scope switch inside the panel, never a Chrome call.
- `CommandExecutor` interface (`run(action, binding) -> outcome`): `ChromeTabExecutor` (worker, primary) and `ReaderExecutor` (fallback 2). Port, controller and tests are shared.
- **Fallback 1, visible docked window**: `windows.create({type:'popup', url:'sidepanel.html'})` placed beside the page by a helper; same page/worker/port; page has `sender.tab` (allowed, 3.1), can be minimized/occluded (existing hidden rule fails closed), binds the active tab of a DIFFERENT window. Trigger: the panel cannot hold camera+tracker visibly across tab switches in a human trial.
- **Fallback 2, in-app reader**: only if both real loops fail; record the failing evidence first. Bundled static pages inside Motif, same tiles, never described as browser control.
- **Hidden rule unchanged.** `FaceTracker` reports stale and `MotifSession.setHidden` fails closed when `document.hidden`. A closed panel destroys the page; nothing can reopen it by gesture (`sidePanel.open` needs a real user gesture, camera events are not user activation, a worker cannot self-grant host access). Reopen = helper clicks the toolbar icon (`openPanelOnActionClick`). While closed no command can exist.
- **Single runtime**: inside the extension origin a Web Lock `motif-runtime-v1` (`ifAvailable`) is held for the page lifetime; a second copy shows a notice and starts no tracker. A second tracker in the localhost web app cannot be technically prevented: operating rule + human-pending check.
- **Camera grant fallback (B5)**: if the panel cannot show Chrome's camera prompt (U2), a helper opens a SEPARATE minimal `grant-camera.html` (calls `getUserMedia`, stops every track immediately, no tracker, no lock, no care client, no messaging). `sidepanel.html` is never opened in a tab for this. The grant is per-origin so it should cover the panel (unverified). The worker's sender check requires pathname `/sidepanel.html`, so the grant page cannot issue commands (test in 7).

## 3. Message protocol and security
### 3.1 Trust boundary
Only the Motif controller page may issue commands. The worker handles a message only if ALL hold: it came through `runtime.onMessage` (no `onMessageExternal`, `onConnect`, `externally_connectable` or content scripts, so web pages cannot reach it); `sender.id === runtime.id`; `sender.origin` equals the extension origin; `new URL(sender.url).pathname === '/sidepanel.html'`; `sender.frameId === 0`; `sender.tab`, if present, is not the bound target tab. The injected scroll function runs in the isolated world with numeric arguments; its return value is untrusted: it is accepted only if it is an object whose `before`, `after`, `height` are finite numbers (else [execution-failed]).

### 3.2 Messages (versioned JSON, panel to worker)
`motif/bind {v:1, panelId, identityKey, accessEpoch, tabId, windowId, origin}`; `motif/command {v:1, panelId, command: BrowserCommand, ttlMs}` for `scroll-up|scroll-down|back`; `motif/release {v:1, panelId}`. `panelId` is a random UUID per page load; `identityKey` is `participant:<id>` or `local`. No credentials or tab URLs go in any message, and nothing from any tab (URL, origin, title) is ever passed to the care client (spy test, 7). Binding: the panel calls `tabs.query({active:true, lastFocusedWindow:true})`, shows the resulting origin in the card ("Controlling: en.wikipedia.org"), and the worker re-reads `tabs.get` to confirm status `complete`, top-frame origin and `permissions.contains`.
**Origin comparison is exact scheme + host + port** (parsed `URL.origin`, never string prefix or `*`): `http://127.0.0.1:3000` never matches `:4000`.
`return-to-communication` is NEVER sent to the worker: `port.execute({action:'return-to-communication'})` is handled locally (validates like any command, calls `host.returnToCommunication()`, resolves `executed` only if it returned true, else `rejected`/[wrong-scope]); a test spies `runtime.sendMessage` and proves it is not called.

### 3.3 `createBrowserCommandPort` (panel side, implements frozen `BrowserCommandPort`)
Validation order before any send (code in brackets): version 1 [bad-version]; `id` non-empty string of at most 64 chars [bad-id]; `action` is an own key of the whitelist (no prototype keys) [unknown-action]; all numbers finite; `issuedAtMs <= now+50`, `expiresAtMs > now`, `0 < expiresAtMs-issuedAtMs <= 1000` [invalid-times/expired/not-yet-valid], default TTL 600 ms on the controller monotonic `performance.now()` clock; `inputEpoch === host.inputEpoch()`, `accessEpoch === host.accessEpoch()`, identity key equals the bound key [stale-input-epoch/stale-access-epoch/identity-changed]; `host.scope() === 'browser'` and a binding exists for tab actions [wrong-scope/not-bound]; nothing else in flight [busy], never queued; id not among the last 256 accepted [duplicate] - recorded on acceptance, so a failed command is never retried under the same id.
`invalidate()` cancels pending work only: rejects the in-flight promise [invalidated], is idempotent, keeps the replay memory. `release()` (my concrete class, not in the frozen interface) also unbinds and sends `motif/release`. A call already inside Chrome (one scroll or goBack, tens of ms) cannot be recalled; the check right before the call is the bound, and the result is reported rejected/[invalidated], never as success. Late replies change no UI state.

### 3.4 Worker validation (honest scope)
The worker has no clock shared with the panel and cannot know the live input state, so it validates what it can: sender (3.1) -> shape/version/whitelist -> `panelId`, `accessEpoch` and `identityKey` equal the stored bind-time values -> `command.inputEpoch` is not lower than the highest inputEpoch already seen from this panelId (monotonic, catches reordered messages) -> id not in the stored last-256 set -> **deadline = `Date.now() + ttlMs` taken on receipt and compared after EVERY await** (storage read, `tabs.get`, `permissions.contains`) and immediately before the Chrome action, [expired] if passed -> live checks: tab exists, `status==='complete'`, the window's active tab is the bound tab, URL present and origin exactly equal [page-changed], `permissions.contains` [permission-missing] -> action with `frameIds:[0]`. Staleness (a changed access epoch, a tracking-loss, an identity change) is the PANEL's job: it sends `release` on every invalidation that drops scope, so the worker's binding disappears; the worker never claims independent epoch enforcement beyond bind-time consistency. Missing `url` or any `loading` change on the bound tab counts as "left the origin" and clears the binding.
Serialization and lifecycle: `onMessage` is registered synchronously at worker top level, the handler returns `true` and calls `sendResponse` exactly once; handling is serialized through a promise queue so replay-set and binding reads/writes in `storage.session` cannot race. A worker that is suspended mid-session loses nothing important (state lives in `storage.session`; a missing binding yields [not-bound]).

### 3.5 Codes and user text
`bad-version bad-id unknown-action invalid-times expired not-yet-valid stale-input-epoch stale-access-epoch identity-changed wrong-scope not-bound busy duplicate sender-rejected invalidated timeout page-loading page-changed tab-closed permission-missing unsupported-page no-history cannot-scroll worker-unavailable execution-failed`.
- **worker-unavailable**: `sendMessage` rejects ("Receiving end does not exist", port closed, worker failed to start). Fail closed, no retry, binding dropped, explanation shown.
- **execution-failed**: the default for ANY other `executeScript`/`goBack` error.
- **unsupported-page**: refused-injection errors including `chrome://`, `chrome-error://` (offline/error pages), Web Store, PDF viewer, `file://`, other extensions' pages.
- **page-changed** also covers "Frame with ID 0 was removed" (verified V5). **no-history**: goBack at the start.
Each code has one plain-language line, shown in the card and announced via aria-live; e.g. unsupported-page: "Motif cannot control this page. Chrome's own pages, the Web Store, the PDF viewer and local files cannot be controlled, and other sites need a helper to allow them first. You are back on your messages."
Back landing on another page: if Chrome reports success the result is `executed` (it did happen); the controller then sees the origin change (3.6) and returns automatically to communication with the reason "left the allowed site".

### 3.6 Invalidation (invariant: a binding exists IFF the session snapshot scope is `browser`)
The controller reconciles on every session snapshot and on `onFailClosed`. Every epoch bump calls `port.invalidate()` (cancels in-flight). It additionally releases the binding and calls `host.returnToCommunication()` when: tracking is not `tracked`, camera not `running`, document hidden (`visibilitychange`, `pagehide`, `freeze`), lock lost, the session scope is no longer `browser` (mapping/profile/stage change, recalibration), identity change (3.7), the bound tab is deactivated/removed/replaced, the tab URL is missing or loading, the origin changed (exact comparison), `permissions.onRemoved`, panel unload. Same-origin in-page navigation cancels only the in-flight command and keeps the binding. **Pause/Resume** (also by the Pause tile) cancels in-flight and bumps the epoch but keeps scope and binding; resuming needs the existing fresh neutral. **Idle**: with valid tracking and no command for 3 minutes (constant, configurable, announced via aria-live before it happens and when it happens) the controller returns to communication. Poll failure or session expiry wipes access without an epoch bump (observed in `CareService`); the identity-key rule below drops browse then. This is intended fail-closed behavior, documented as a limitation (a network blip ends browsing).

### 3.7 Identity (no second login system)
The panel runs the shared `createSupabaseCareClient` (one SDK per visible surface, awaited disposal before replacement). No credential, token or profile is copied between origins: `chrome-extension://<id>` has its own storage, so a helper pairs the participant, and calibration/profiles are made or restored, INSIDE the panel. Browser scope is available to roles `participant` and local use (`signed-out`/`unpaired`); never `caregiver` or `revoked`. `accessKey = epoch + role + participant.id` is recomputed on each snapshot; any difference from the bound key invalidates and releases. A new person at the camera needs the existing disarm and calibration revalidation, not just a new label. The Return handler reads the live snapshot, so it can only reveal the communication view of the CURRENT authorized participant.

## 5. Scan scopes, Pause, Return and latency (B1)
- `communication` scope = existing list plus a `browse` tile when a controller is attached. `browser` scope = exactly five tiles in this fixed order: `Scroll down` (0), `Scroll up` (1), `Back` (2), `Pause` (3), `Return to messages` (4). That is "4 commands plus Pause" (Pause present whenever communication has one - it always does). **No speed controls** in browser scope; users Return first to change speed.
- Worst-case latency, scan interval T (default 2 s, range 1-6 s, plus the existing activation dwell ~0.25 s): from entry (index 0) Pause arrives at 3T and Return at 4T; from any position any tile is reached within 4T because the list wraps (8 s + dwell at default). Step mode (Next/Previous mapped): at most 4 Next, or 2 moves with Previous mapped; select-only mapping uses auto scan and the 4T bound. Tests assert these bounds with a fake clock.
- Pause/Resume keeps scope, cancels in-flight, bumps the epoch (3.6). Select-only mappings and the assisted Space driver both reach Pause and Return (patch tests).
- **Every path that rebuilds the scanner goes through scope-aware target building** (Hook 1): `enterCommunication(keepScope)`, `enterPractice`, `fallBackToAutomatic` (step idle fallback keeps scope via `enterCommunication(true)`), `restrictedScanner` for tiring/mapping/recalibrate/add-movement (leaves communication stage; `setStage` resets scope to `communication`), `useAssisted`/`useGesture`, and `setBrowserSink`/`enterBrowserScope`/`returnToCommunication` all call the single `routedTargets()`/`rebuildRouted()`. `changeInterval` (slower/faster) only calls `scanner.setInterval` and cannot happen in browser scope because those tiles are absent.
- One event, one effect: `dispatchTarget(id)` is the only path from a selected tile to an effect and yields exactly one of care / browser / local; browser tiles never call the care client; care tiles never reach the port; the port also checks scope. Scope changes restart the scanner (fresh neutral).
- Return: scope switch only; care client and request state are never unmounted, so request status persists. Works with no binding, revoked permission or unsupported page. Every invalidation performs it with a visible reason. Active mappings: the card lists the five tiles and which movement/switch selects (reusing `describeMapping`), the state, and the bound origin.

## 12. Implementation notes (chunks 1-7; no design change, recorded for the tester)
- CSP: `style-src 'self'` (no `unsafe-inline`) was enough; the full app booted with zero `securitypolicyviolation` events across load, model, camera, audio cues, speech announcements and video (smoke). Chrome's default `blob:` for `connect-src` is kept to match the root policy shape.
- Tailwind scanning: the extension build uses Vite root `extensions/motif`, so Tailwind does not scan `src`; no Tailwind utility classes are used in `src` (only custom classes), so the CSS is equivalent (26.6 kB vs 30.3 kB in the root build, the difference being stray generic utilities generated from words in docs).
- `URL.origin` of `chrome-extension://` URLs is `"null"` in Node and jsdom, so the sender check builds `protocol//host` itself.
- A cancelled pending hold bumps the input epoch (patch hook 2), so a legitimately executing first scroll can be reported `invalidated`. Conservative, not a bug.
- The controller defers every scope change with `queueMicrotask` (the failClosed listener fires inside `route()`/`setHidden`), but calls `port.invalidate()` synchronously. Its own Browse -> browser transition (which bumps the epoch) is excluded from fail-closed handling.
- Known limits, not built: (a) fallback 1 (docked window) needs a window choice because `lastFocusedWindow` may be the Motif window; (b) Chrome match patterns may ignore the port, so a grant for `https://host:8443` may cover other ports, while Motif still compares the exact origin including port before every action; (c) a network blip or expiry ends browsing (fail closed); (d) the worker drops the binding if a command arrives while the page is loading.
- Unverified still: U1 real side panel and visibility; U2 camera prompt in the panel; U3 optional-permission request is not answerable headlessly (the probe build grants 127.0.0.1 at install, the shipped manifest has none); U4 branded Chrome 155 load; U5 documentation recall.

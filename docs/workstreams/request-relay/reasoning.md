## Database

- public.care_groups: UUID id, unique owner_id, name, created_at. Owner is an authenticated non-anonymous caregiver from signed claims; never user_metadata or a UI flag.
- public.participants: UUID id, group_id, alias, unique nullable user_id until paired, revoked_at, created_at. Anonymous Supabase Auth users can redeem a scoped invitation; cannot create caregiver groups. No silent identity rebinding.
- public.care_requests: UUID id (client idempotency key), server-derived participant_id/group_id, kind water/bathroom/reposition/help, status sent/acknowledged/completed/cancelled, revision and server timestamps. No free text or camera data.
- Private invite and attempt tables: hashed random tokens only, raw token returned once to owning caregiver, ten-minute expiry, atomic single redemption and bounded attempts per anonymous identity/window. Invalid/rate-limited redemption returns explicit failure instead of an exception that rolls back attempt accounting. Provider auth limits complement this; do not claim abuse-proof rate limiting.
- Clients have RLS SELECT only on group/participant/request tables and no direct mutations. Caregivers see own group, participants and requests; paired participants see own binding/revocation state and own requests only while active. Invitation/attempt data is never selectable. All mutations use security-definer RPCs with empty search_path, fully qualified names, ownership/state checks, PUBLIC/anon execute revoked, necessary authenticated grants only. No service-role key in browser.

RPC names/inputs: motif_access(), motif_create_group(p_name), motif_create_participant(p_alias), motif_create_invite(p_participant_id), motif_redeem_invite(p_token), motif_revoke_participant(p_participant_id), motif_send_request(p_request_id,p_kind), motif_transition_request(p_request_id,p_revision,p_status), motif_clear_group(). All inputs/outputs are versioned shared contracts. Invalid sender/group IDs cannot be supplied to Send; derive them from auth.uid(). Caregiver operations stay within own group. Participant can cancel own nonterminal requests; caregiver can acknowledge sent then complete acknowledged. Terminal states stay terminal; stale revisions fail. Same caller/request ID/kind retry returns original record; mismatched payload/other caller fails without disclosure. Clear group revokes pairings/invites and deletes session requests; document exact retention behavior.

Revision 2 notification choice: use an honest two-second authorized polling watch for this foundation, NOT Postgres Changes subscriptions. Do not create/add care tables to any Realtime publication, change global publication settings or open a websocket. Supabase DELETE events do not enforce RLS; avoiding that stream prevents cross-group deletion metadata. Each poll re-fetches motif_access and RLS-protected snapshot lists; failures report disconnected and clear inaccessible state. Own binding remains readable after revocation so it can clear request access; DB immediately denies later request operations. No broadcasts/channels or durable auto-retry queue. Document polling timing and hosted-provider limits, not instantaneous updates. A later Realtime design needs separate review.

## Client

src/care/contracts.ts exports version 1 models, AccessState (signed-out/unpaired/caregiver/participant/revoked), connection/config states and CareClient operations. Operations cover access, caregiver password sign-in/sign-out, anonymous participant sign-in/redeem, group/participant/invitation management, authorized lists, send/transition/clear, watch/dispose. Runtime-validate all server responses; errors never become Sent.

src/care/client.ts uses real Supabase Auth/RPC/select with injected SDK boundary for deterministic tests. Factory constructs the actual SDK. Verify initial identity through getUser and server motif_access; polling server motif_access is authenticated by PostgREST and avoids repeated getUser traffic. Never trust a local role flag. Auth callbacks schedule refresh outside the callback and never apply the callback's identity payload directly. Serialize ALL auth-changing SDK calls on one queue per client (including sign-out, anonymous sign-in/redeem and caregiver sign-in). Immediately invalidate the app epoch/clear private state when an auth operation is requested, but execute SDK mutations strictly sequentially; old results cannot become current while a newer request is queued. Auth notifications reconcile actual current SDK/server access through the queue and do not re-run old sign-in payloads. Do not construct multiple SDKs with the same storage key in one control surface. Cross-tab provider session notifications invalidate old app state and reconcile current server identity; no simultaneous different identities sharing one persisted browser session are promised. Test deferred sign-in A, queued B and delayed A callback to show both SDK persisted identity and app state end at B.

All data dispatch (send/transition/clear included) shares the serialized queue with auth operations. Capture current authorized identity/epoch when a command is requested; recheck before dispatch and after completion. An auth change invalidates queued older work immediately, while already-dispatched work completes/aborts before the next SDK identity mutation. Pin the captured access JWT explicitly on each PostgREST HTTP request, so a different tab's SDK session change cannot make an old action run as a new user. Supabase SDK supplies Auth; a small real PostgREST fetch adapter with explicit apikey/Authorization and abort/timeout handling supplies data. Tokens stay private, never in snapshots/logs. Tests delay token acquisition/HTTP dispatch then request account B and show an A action is rejected or remains under A, never B.

Watch polls do not overlap, discard late epoch/generation results and stop timers on disposal/sign-out. Expose session/access invalidation so UI/extension consumers cancel stale commands. Supabase sign-out revokes refresh access but existing access JWTs may remain valid until expiry: claim immediate local cleanup, not global JWT invalidation. Pairing revocation is a separate DB gate that denies participant requests even with an unexpired JWT. Never copy credentials to ordinary-page messages. UI mounting remains teammate work; export usable real adapters and usage instructions.
